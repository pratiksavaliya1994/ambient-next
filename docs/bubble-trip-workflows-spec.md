# Bubble Studio spec: the trip workflows

A build sheet for phase 4 — three new types and eight new workflows, written to
be handed to whoever builds them in Bubble Studio without the surrounding
Next.js context. Read [`phase-4-trips.md`](./phase-4-trips.md) for why.

**Status: not built.** `lib/bubble/trips.ts` calls all six public endpoints
today, so until these exist every trip action fails with a visible error. The
read side degrades quietly instead — `bubbleListMaybeMissing` turns a 404 into
an empty list, which is why §1's "does `GET /obj/trip` 404?" check matters.

> The `version-test` branch is the only version in use. Treat it as
> production: ~1,477 jobs, ~1,550 requests, 532 tools of real data. Test with
> rows you pick deliberately (§9) — every test run is a real write.

---

## 1. The three new types

Field names are case-sensitive and the Next.js side matches them exactly
(`lib/bubble/trips-read.ts`). `tripID`, `toolID` and `requestID` follow the
existing **id-as-text** convention (`requestedtools.requestID`,
`assignedtools.toolID`) — they are **text fields holding another row's unique
id, not Bubble links**. Don't "improve" them into links; nothing in this app
resolves them that way and the joins are all done in JS.

### `trip`

| Field | Type | Notes |
| --- | --- | --- |
| `idempotencyKey` | text | **Required. See §3 — this field is load-bearing.** |
| `driver` | text | Free text, same as `request.driver` |
| `tripDate` | date | |
| `status` | text | `Planned` · `In Transit` · `Completed` · `Cancelled`. **Text, not an option set** — same call `request.status` makes, so a bad value fails loudly in Zod rather than silently on write |
| `startedAt` | date | |
| `completedAt` | date | |
| `notes` | text | |

### `tripstop`

| Field | Type | Notes |
| --- | --- | --- |
| `tripID` | text | |
| `stopKey` | text | A UUID **generated by the browser**, not Bubble. See §3 |
| `seq` | number | `1..N` |
| `location` | text | A `jobs.name`, or `"Warehouse"`. **Two stops on one trip can carry the same string** — that is a split stop, not a bug |
| `kind` | text | `Warehouse` · `Job` |

### `triptool`

| Field | Type |
| --- | --- |
| `tripID`, `toolID`, `requestID` | text |
| `toolName`, `toolType` | text |
| `fromStopKey`, `fromLocation` | text |
| `toStopKey`, `toLocation` | text |
| `state` | text — `Planned` · `Loaded` · `Dropped` · `Skipped` |

Copy privacy rules from `assignedtools`, the same way `assignedtools` copied
them from `requestedtools`.

**After creating the types**, confirm each returns `{"results":[]}` rather than
a 404:

```
GET /obj/trip      GET /obj/tripstop      GET /obj/triptool
```

A 404 here means the type name is wrong, and `bubbleListMaybeMissing` would
hide that forever as "no trips yet".

## 2. Why one `triptool` row per tool, not one per leg

A tool's whole journey is **one row** — collected at `fromStopKey`, dropped at
`toStopKey`. The alternative (a row per stop-tool-action) was rejected because
Bubble has no transactions and *Schedule API Workflow on a list* demonstrably
half-fails — which is why `create-assigned-tool` is count-checked. With
per-leg rows, a partial fan-out leaves a tool **collected and never dropped**,
indistinguishable from one legitimately still on the truck. In the one-row model
that state cannot be represented.

The per-leg audit trail exists anyway: every leg writes `tools.location`, and
`DB - Tools Change Log` turns each write into a `toolshistory` row.

## 3. Two things that look optional and are not

### `idempotencyKey` on `create-trip`

`lib/bubble/client.ts` retries a POST **up to four times** on 429/5xx. Every
other write workflow in this app survives that because it *deletes first* —
`create-assigned-tool` says so in its own comment. `create-trip` creates a
top-level row and has nothing to delete by, so without this key one retry after
a 502-that-actually-committed is one duplicate trip holding duplicate claims on
real tools.

The guard is a condition on the create steps, **not** a Terminate: a retry must
still return the existing trip's id, or the browser is left with a trip it
cannot open.

### `stopKey` instead of `tripstop`'s own unique id

`save-trip` deletes and recreates every stop, so `tripstop`'s unique id is
destroyed on every save — the same instability that already rules out pointing
at `assignedtools`' id. The browser generates `stopKey` and it survives.

It also means `create-trip` never has to resolve a just-created stop's id inside
an async fan-out, which is the part that would be genuinely awkward in Studio.

## 4. The two private helpers

**Not exposed as public API endpoints** — same setting as `assign-request-tool`
and `update-tool-status`.

> ⚠️ `docs/phase-2a-assignment-handoff.md` records "Expose as a public API
> workflow" being left checked on `assign-request-tool` by accident. Check both
> of these. An exposed helper lets a caller create rows while bypassing the
> delete-first step that makes saving idempotent.

**`create-trip-stop`** — params `tripID` (text), `stopKey` (text), `seq`
(number), `location` (text), `kind` (text). One step: *Create a new tripstop*.
**No** "Return data from API" step.

**`create-trip-tool`** — params `tripID`, `toolId`, `requestId`, `toolName`,
`toolType`, `fromStopKey`, `fromLocation`, `toStopKey`, `toLocation`, `state`
(all text). One step: *Create a new triptool*. No return step.

## 5. `create-trip`

Backend Workflow → API Workflow, exposed, auth "User & admin" (same as
`new-request`).

| Parameter | Type |
| --- | --- |
| `idempotencyKey` | text |
| `driver` | text |
| `tripDate` | date |
| `notes` | text |
| `stops` | **list of objects** — `{ stopKey, seq, location, kind }`, via Detect Data |
| `items` | **list of objects** — `{ toolId, requestId, toolName, toolType, fromStopKey, fromLocation, toStopKey, toLocation }`, via Detect Data |

Define both object types by pasting a sample payload into Detect Data, exactly
as `create-assigned-tool`'s `assignments` was defined.

**Step 1 — Create a new `trip`.**
Condition: `Search for trip (idempotencyKey = idempotencyKey):count is 0`.
Fields: `idempotencyKey`, `driver`, `tripDate`, `notes`, `status = "Planned"`.

**Step 2 — Schedule API Workflow on a list** → `create-trip-stop`.
Same condition as step 1. List: `stops`. `tripID` =
`Search for trip (idempotencyKey = idempotencyKey):first item's unique id`.

> Reference the trip by **searching on the key**, not by "Result of step 1" —
> step 1 is conditional, so on a retry it did not run and its result is empty.

**Step 3 — Schedule API Workflow on a list** → `create-trip-tool`.
Same condition, list `items`, same `tripID` expression, `state = "Planned"`.

**Step 4 — Return data from API:**

```json
{
  "ok": true,
  "tripId": "Search for trip (idempotencyKey = idempotencyKey):first item's unique id",
  "stops": "stops:count",
  "items": "items:count"
}
```

Returning the *searched* id rather than step 1's result is what makes a retry
answer correctly instead of returning empty.

## 6. `save-trip`

Replaces a **`Planned`** trip's whole plan. This is also the reorder write —
dragging stops and pressing Save re-sends everything, which is why there is no
separate ordering workflow and none of `set-request-order`'s async-fan-out race.

| Parameter | Type |
| --- | --- |
| `tripId` | text |
| `driver`, `notes` | text |
| `tripDate` | date |
| `stops`, `items` | as `create-trip` |

**Step 1 — Terminate this workflow.**
Condition: `Search for trip (unique id = tripId):first item's status is not "Planned"`.

> **Load-bearing, not defensive.** Saving is delete-then-recreate. Run against a
> trip already under way it would delete `triptool` rows carrying real-world
> facts (`Dropped`, `Skipped`) and resurrect them as `Planned` — silently
> un-delivering tools that are physically sitting on a job site. The UI hides
> the Save button on a started trip, but `/wf/` endpoints are reachable
> directly, so the UI is not the guard.

**Step 2 — Make changes to a thing** (`trip`): `driver`, `tripDate`, `notes`.

**Step 3 — Delete a list of things:** `Search for tripstop (tripID = tripId)`.

**Step 4 — Delete a list of things:** `Search for triptool (tripID = tripId)`.

**Step 5 / 6 — Schedule on a list** → `create-trip-stop` / `create-trip-tool`,
as in §5 but with `tripID = tripId` directly.

**Step 7 — Return:** `{ "ok": true, "stops": "stops:count", "items": "items:count" }`

Delete-first is what makes this idempotent under `client.ts`'s retry.

> **Steps 5 and 6 are asynchronous.** *Schedule API Workflow on a list* returns
> once the runs are queued, so step 7's `stops:count` / `items:count` report
> what was **sent**, not what has been written — and on a save the old rows are
> already deleted. A run sheet opened in that window shows stops with nothing
> happening at them and tools that render nowhere. Next waits it out in
> `lib/trips/settle.ts` (`waitForTripPlan`) before the action returns; if these
> steps are ever rebuilt synchronously, that wait becomes a no-op rather than
> wrong.

## 7. `start-trip`

| Parameter | Type |
| --- | --- |
| `tripId` | text |
| `driver` | text |
| `toolIds` | text **list** — only the tools collected at the **first** stop |

**Step 1 — Terminate** unless `status is "Planned"`.

**Step 2 — Make changes to a thing** (`trip`): `status = "In Transit"`,
`startedAt = Current date/time`, `driver = driver`.

**Step 3 — Make changes to a list of things** —
`Search for tools (unique id is in toolIds)`:
`statusNew = toolStatus`… **no**: this workflow writes a fixed value, so set
`statusNew = "In Transit"` (`:converted to ToolStatusNew`),
`location = driver`, `currentUser = driver`.
**Gate the whole step on `toolIds is not empty`.**

**Step 4 — Make changes to a list of things** —
`Search for triptool (tripID = tripId, toolID is in toolIds)`: `state = "Loaded"`.
Same gate.

**Step 5 — Return:** `{ "ok": true, "tools": "toolIds:count" }`

Step 3's edit to `tools` is what triggers `DB - Tools Change Log`, which writes
one `toolshistory` row per tool. **Do not add an explicit history step** — that
produced duplicates once already; see
`docs/bubble-update-request-status-spec.md`'s 2026-09-10 note.

## 8. `complete-trip-stop`

One stop, five outcomes, one call.

| Parameter | Type |
| --- | --- |
| `tripId`, `stopKey`, `driver` | text |
| `dropStatus` | **the `ToolStatusNew` option set**, not text |
| `dropLocation` | text |
| `dropToolIds`, `loadToolIds`, `skipToolIds` | text **lists**, each optional |
| `refuseToolIds`, `returnToolIds` | text **lists**, each optional — the refused-drop pair, §8.1 |

> ⚠️ **`stopKey` is passed for the Bubble log only and must never be read by any
> step.** Next.js sends the literal `#return` for a synthesised terminal warehouse
> stop that has **no `tripstop` row** — the stop a refused tool is carried home to
> on a route that would otherwise end at a job site. A step that searched
> `tripstop` by `stopKey` would find nothing, and because every list action over
> an empty list is a silent no-op there would be no error, no empty-`response`
> refusal and no count mismatch to catch it. It would surface weeks later as
> "that stop just doesn't tick".

`dropStatus` is declared as the option set **type itself** for the same reason
`update-request-status`'s `toolStatus` is: Bubble then matches the display text
and raises on a bad value, where text-and-convert-later reproduces the Data
API's silent-failure behaviour.

> **Why `dropStatus` is a parameter at all.** It is what makes a pickup and a
> delivery the same code path. Next.js reads it off the stop's stored `kind`:
> a `Job` stop drops tools as `Delivered`, a `Warehouse` stop drops them as
> `Available` — back in the yard and free again. No per-tool branching anywhere.

Steps, each gated on its own list being non-empty (step 10 stands alone — it has
no `tools` half by design):

1. **Terminate** unless `status is "In Transit"`.
2. `tools` where `unique id is in dropToolIds`: `statusNew = dropStatus`,
   `location = dropLocation`. **Do not set `currentUser`** — it stays the
   driver, a real record of who moved it, matching offload's long-standing rule.
3. `triptool` where `tripID = tripId` and `toolID is in dropToolIds`:
   `state = "Dropped"`.
4. `tools` where `unique id is in loadToolIds`: `statusNew = "In Transit"`,
   `location = driver`, `currentUser = driver`.
5. `triptool` … `toolID is in loadToolIds`: `state = "Loaded"`.
6. `tools` where `unique id is in skipToolIds`: **`statusNew = "Pickup
   Requested"` and nothing else.** No `location`, no `currentUser` — the tool
   keeps the site it was never collected from. This is exactly the contract
   `leaveToolsBehind` had.
7. `triptool` … `toolID is in skipToolIds`: `state = "Skipped"`.
8. `tools` where `unique id is in returnToolIds`: `statusNew = dropStatus`,
   `location = dropLocation`. **Do not set `currentUser`** — same rule as step 2.
9. `triptool` … `toolID is in returnToolIds`: `state = "Returned"`.
10. `triptool` … `toolID is in refuseToolIds`: `state = "Refused"`.
    **There is deliberately no `tools` step to pair with this one** — see §8.1.
11. **Return:**

```json
{
  "ok": true,
  "dropped": "dropToolIds:count",
  "loaded": "loadToolIds:count",
  "skipped": "skipToolIds:count",
  "refused": "refuseToolIds:count",
  "returned": "returnToolIds:count"
}
```

### 8.1 The refused-drop pair

A site can turn a delivery away. The driver unticks it, exactly as they untick a
collect they couldn't take, and the two outcomes are mirror images:

| | collect fails | drop fails |
| --- | --- | --- |
| list | `skipToolIds` | `refuseToolIds` |
| `triptool.state` | `Skipped` | `Refused` |
| `tools` write | `statusNew = "Pickup Requested"` | **none at all** |

**Step 10 writes nothing to `tools` on purpose.** A refused tool is in the van:
`In Transit` at `location = driver`, which is already what the row says and stays
true until it is unloaded. Writing anything would be a lie, and would fire a
misleading `DB - Tools Change Log` row.

The tool then rides to a `Warehouse`-kind stop — one the route already visits, or
a synthesised terminal one — where the driver drops it like anything else. Next.js
splits that tick into `returnToolIds` (rows already reading `Refused`) and
`dropToolIds` (ordinary ones) by re-reading each row's live state; the browser
never names the return list.

**Why two lists and not one `dropState` parameter.** On
`W#collect → Job A → W#drop`, a refusal at Job A rides on to `W#drop`, which was
already going to take a planned pickup. That single call has to write `Dropped`
for the pickup tool and `Returned` for the refused one — both with
`dropStatus = Available` and `dropLocation = Warehouse`. One text parameter cannot
be two values. Two disjoint lists also mean no step ever double-writes
`triptool.state`, and step 3 keeps its literal `"Dropped"`, so an older client
sending no new parameter can never blank a state.

**These steps are purely additive: no existing step changes.** That is what makes
the Studio edit safe to save before the app ships — an older client sends neither
list, steps 8–10 gate off on empty, and the two extra return keys are ignored by
`z.looseObject`. The reverse order is **not** safe: an app sending `refuseToolIds`
at a workflow without it gets a return with no `refused` field and throws in
`stopResult.parse` *after* the drops and loads have already committed.

## 9. `complete-trip` and `cancel-trip`

**`complete-trip`** — param `tripId`. Terminate unless `status is "In Transit"`.
Set `status = "Completed"`, `completedAt = Current date/time`.
Return `{ "ok": true }`.

The "are any tools still on the truck?" check lives in Next.js, so the message
can name them.

**`cancel-trip`** — param `tripId`. **Terminate unless `status is "Planned"`** —
a trip that left the yard happened and cannot be un-happened. Then delete
`Search for tripstop (tripID = tripId)` and
`Search for triptool (tripID = tripId)`, and set `status = "Cancelled"`.
Return `{ "ok": true }`.

## 10. One addition to `new-pickup-request` (phase 3B)

Three changes to the **existing** workflow, and **one new parameter**. No new
workflow, no object parameters, no `::` codec.

> **Revised 2026-09-15.** An earlier draft of this section asked for an
> `assignments` parameter carrying `{ toolId, extra, toolType }` objects via
> Detect Data, mirroring `create-assigned-tool`. That was dropped when the live
> workflow turned out to take everything as text/primitives — and the
> replacement is better, not merely simpler: see the note under step 2.
> **The Next.js side sends `toolIds` and nothing else.**

- **New parameter `toolIds`** — type **text**, **list** ticked. The workflow's
  only addition. It sits alongside the existing `toolStatusUpdates` text list,
  so the parameter tab keeps one shape throughout.

- **On the existing *Create a new request* step:** `status = "Assigned"` (plain
  text). A pickup names its tools at creation, so it is born ready to collect.

- **Schedule API Workflow on a list** → the existing **private**
  `assign-request-tool`. Only when `toolIds is not empty`.

  | Field | Value |
  | --- | --- |
  | Type of things | **tools** |
  | List to run on | `Search for tools (unique id is in toolIds)` |
  | `requestId` | the *Create a new request* step's result's unique id |
  | `toolId` | `This tools's unique id` |
  | `toolType` | `This tools's name` |
  | `extra` | `no` |

  > **The list is a search, not the parameter.** That is the whole trick, and
  > why no object parameter is needed: fanning out over `tools` rows rather
  > than over texts means each iteration *has* the tool, so the two values an
  > object would have carried are read from the row itself at write time.
  >
  > It is also strictly safer than sending them. A tool renamed between page
  > load and submit writes its **current** name, and a forged POST cannot put
  > an arbitrary string in `toolType` or set `extra = yes` — the browser only
  > ever gets to choose *which rows*, never what is written about them.
  >
  > Two consequences worth knowing rather than discovering: a `toolId` that no
  > longer exists is silently skipped by the search (no row, no error), and a
  > duplicated id yields one row, not two. Both are the behaviour you want
  > here — a pickup names each physical tool once.

  > Fan out the **private** helper, not the public `create-assigned-tool`: the
  > public one begins by deleting the request's existing rows, which is
  > pointless on a request created three steps earlier.

- **Make changes to a list of things** — `Search for tools (unique id is in
  toolIds)`: `statusNew = "Pickup Requested"` (`:converted to ToolStatusNew`),
  only when `toolIds is not empty`.

  > Nothing wrote `Pickup Requested` before this. It existed in the option set
  > and in the dashboard's badge map, but no workflow produced it.

  > The same search runs twice, which is deliberate — a synchronous list-change
  > for the one field every tool takes identically, and a fan-out for the rows
  > whose values differ per tool. That is the split
  > `bubble-update-request-status-spec.md` sets out, applied here.

`assignedtools.toolType` for these rows holds the **physical tool's name**, not
a `toolstype` name. That is the field's documented meaning for a pickup — the
`toolsSummary` entries *are* physical names — and it is what lets `buildSlots`
count "3 of 5 collected" with no new logic. Don't "fix" it.

> ✅ **Built and verified end to end on 2026-09-15**, against §11's test 9: one
> `assignedtools` row per checked tool with the physical name in `toolType` and
> `extra = no`, `request.status = "Assigned"`, every checked tool at
> `Pickup Requested`, and `condition` written only where the PM changed it.
>
> ⚠️ **`toolType` was first wired to `This tools's type's name`** — the tool's
> *category* — and corrected during the build. Both expressions are valid and
> both yield a plausible string, so nothing looks wrong at the row level; what
> breaks is `buildSlots`, which counts a pickup's progress by matching
> `assignedtools.toolType` against `toolsSummary` entries that **are** physical
> names. Every row present and "3 of 5 collected" reading 0 of 5. That is the
> failure mode the paragraph above is guarding against, and it has now happened
> once.

## 11. Test before relying on any of it

Every run is a real write. Note the rows you pick and put them back.

1. **`create-trip`**, 2 stops / 3 items → one `trip`, two `tripstop`, three
   `triptool`; counts in the response match. **Then re-POST the identical
   payload, same `idempotencyKey` → still one trip, and the same `tripId` comes
   back.** This is the single most important test on the page.
2. **`save-trip`** with 3 stops / 4 items → exactly 3 and 4 exist, the previous
   rows gone. Re-send identical → still 3 and 4.
3. Set that trip's `status` to `"In Transit"` by hand, then call `save-trip`
   again → **must terminate and change nothing.** Verify by reading the rows
   back, not by trusting the response.
4. **`start-trip`** on two deliberately-chosen tools → `trip.status`/`startedAt`;
   both `tools` rows at `In Transit`, `location`/`currentUser` = the driver;
   both `triptool` rows `Loaded`; and **exactly one** new `toolshistory` row per
   tool (`GET /obj/toolshistory?sort_field=Created Date&descending=true&limit=5`)
   with `prevStatusNew`/`newStatusNew` populated.
5. **`start-trip` with an empty `toolIds`** → count `toolshistory` before and
   after; **must be identical**. This is the empty-list guard.
6. **`complete-trip-stop`** with one id in each of the three lists → three
   different outcomes on three tools. Specifically confirm the **skipped** tool's
   `location` and `currentUser` are **untouched** and only `statusNew` moved.
7. The same call with `dropStatus = Available` and `dropLocation = "Warehouse"`
   → the tool reads `Available` there **and its `condition` is unchanged**. That
   last part is what the whole 3A condition split exists for.
8. **`complete-trip`** then call it again → second call terminates.
   **`cancel-trip`** on a `Planned` trip → `Cancelled`; on an `In Transit` trip
   → terminates.
9. **`new-pickup-request`** — create one pickup request for a job whose tools
   you noted first. Confirm one `assignedtools` row per checked tool with the
   physical **name** in `toolType` and `extra = no`; `request.status =
   "Assigned"`; every checked tool `statusNew = "Pickup Requested"`; and
   `condition` written **only** on tools whose condition was actually changed.
